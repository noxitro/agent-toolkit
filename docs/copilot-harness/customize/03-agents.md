# 3. カスタムエージェント — 役割を固定し、分業させる

カスタムエージェントは、役割(人格・守る規則・使えるツール・報告の形式)を固定した Markdown + YAML frontmatter の定義。
人が選んで会話の相手にすることも、本体のエージェントが作業の一部を**委譲**して、別の文脈で走らせることもできる(サブエージェント)。
ユーザーハーネス(第 5 章)の実装役と審査役は、この部品で作る。

この章で持ち運べるのは**設計**(役割を分ける、審査役を読み取り専用にする、同じモデル・似た指示にしない)であって、**ファイルの書式ではない**。
Claude Code・OpenCode・Codex もカスタムエージェントを持つが、置き場も frontmatter も別物(付録 E)。

## 3.1 仕組み

- 定義ファイルは `.agent.md` 拡張子の Markdown ◎。frontmatter に役割の設定、本文にプロンプト(30,000 字以内 ◎)。
- **選ぶ**: `/agent` で一覧から選ぶ、依頼文の中でエージェント名を挙げる、起動時に `--agent=<name>` を付ける ◎。
- **委譲される**: 本体が「このエージェントの得意分野に合う」と判断すると、サブエージェントを立ち上げて任せる ◎。判断材料は `description`。
- サブエージェントは**独自の文脈ウィンドウ**を持ち、本体の文脈を汚さない ◎。並列にも走れる ◎。深さと同時数には上限がある ◎。
- 委譲で呼ばれたときは、既定ではリポジトリの指示ファイルを受け取らない ◎。`include-custom-instructions: true` で受け取る(人が選んだときは既定で読む)◎。

## 3.2 Copilot での置き場と優先(2026-10 時点 ◎)

| 優先 | 場所 | 備考 |
| --- | --- | --- |
| 1(最優先) | `~/.copilot/agents/<name>.agent.md` | 個人用。**リポジトリより優先される** |
| 2 | `.github/agents/<name>.agent.md` | リポジトリ。作業ディレクトリから git ルートまで探す |
| 3 | `.claude/agents/` | 他環境由来の形式 |
| 4〜6 | `--add-dir` の `.github/agents/`、プラグイン同梱、組織・エンタープライズ | |

- エージェント ID はファイル名(拡張子を除く)。サブディレクトリに置くと `team--reviewer` のように `--` で連結される ◎。
- 同じ ID が複数あれば**先に読まれた方**(個人用)が使われる ◎。チームで使う定義と同名のものを `~/.copilot/agents/` に置かない。
- **アプリ**では `/agent` で選ぶ ◎。アプリが `.github/agents/` を直接読むかは公式文書に明記が無い ▲。CLI 基盤なので読むと推測しているが、手元の環境で確かめる(第 3.6 節)。
- `copilot --agent=<name> --prompt "..."` で非対話でも使える ◎。エージェントの一覧・追加・削除には非対話コマンドが無い ◎(セッション内の `/agent` で行う)。

## 3.3 frontmatter

```yaml
---
name: reviewer
description: 実装済みフェーズを HARNESS.md のゲート条件で検証し、証拠付きで PASS/FAIL を判定する読み取り専用の審査役。コードは直さない。
tools: ["read", "search", "execute"]      # edit を入れない
include-custom-instructions: true
---
```

| キー | 意味 | 注意 |
| --- | --- | --- |
| `description`(必須) | 一覧に出る説明。**委譲の判断にも使われる** ◎ | 「何をする役か」と「何をしないか」を 1〜2 文で |
| `name` | 表示名。`--agent` で指定できる ◎ | 省くとファイル名。ファイル名と揃える |
| `tools` | 使えるツールの配列。省くと全部 ◎。`*` を含めると全部 ◎。`[]` で全部禁止 ◎ | 名前の書き方は表の下 |
| `model` / `models` / `modelPolicy` / `reasoningEffort` | モデルの指定と推論強度 ◎ | `model` / `models` / `reasoningEffort` は省くと本体と同じ。`modelPolicy` の既定は `preferred` ◎。原則省略し、固定が要ると分かってから書く |
| `disable-model-invocation` | true で自動委譲を禁止(人が選ぶ専用)。共通リファレンス ◎ | 旧キー `infer: false` と同じ。共通リファレンスは `infer` を廃止扱い ◎ だが、CLI のリファレンスには `infer` だけが載っている ◎。CLI でどちらが効くかは手元の環境で確かめる △ |
| `user-invocable` | false で人が選べなくする(委譲専用)。共通リファレンス ◎ | CLI での効き方は手元の環境で確かめる △ |
| `mcp-servers` | このエージェント専用の MCP 設定 ◎ | 書式は `~/.copilot/mcp-config.json` と同じ |
| `include-custom-instructions` | 委譲時にリポジトリの指示を読む ◎ | 実装役・審査役には true |

`tools` に書く名前 ◎:

- エイリアス: `execute`(シェル)、`read`、`edit`、`search`、`agent`、`web`、`todo`
- MCP のツール: `サーバー名/ツール名` か `サーバー名/*`
- **知らない名前は黙って無視される。** 綴りを間違えても警告は出ない(第 3.7 節)

本文には「守ること」と「報告の形式」だけを書き、作業手順は HARNESS.md とスキルに任せる。手順まで書くと、HARNESS.md を直したときにエージェント本文との食い違いが起きる。

## 3.4 設計の原則

### 役割を 2 つに分ける

| 役割 | 一言で | 雛形 |
| --- | --- | --- |
| 実装役 | スコープ内を作り、ビルド・テスト・自己検証を通し、定型で報告する。コミットしない。テストコードを変えない | [templates/implementer.agent.md](templates/implementer.agent.md) |
| 審査役 | 自分で測り直し、陽性コントロールと意地悪テストを経て VERDICT を返す。**コードを直さない** | [templates/reviewer.agent.md](templates/reviewer.agent.md) |

### 審査役を読み取り専用にする(三重化)

ここで使う語: **オーケストレータ**は 1 周を回す本体のチャット(第 5 章)。**陽性コントロール**は、わざと壊した実装で FAIL が出ることの確認(第 5 章 Step 5)。
**意地悪テスト**は境界値や空入力など、ゲート条件の文言の外側を試すこと。

「直さない」は 1 つの仕組みでは保証できない。

| 層 | 仕組み | 抜け道 |
| --- | --- | --- |
| 1. ツール制限 | `tools` から `edit` を外す | `execute` があればシェル経由で書ける。`execute` を外すと測り直しができないので両立しない |
| 2. 指示本文 | 「ファイルを書かない。直したくなったら FAIL」 | 指示は確率的に守られる。実測では「直接直せ、シェルで書いてよい」と頼んでも編集せず FAIL を返した △(1 回) |
| 3. 外側の git diff 比較 | オーケストレータが審査の**前後**で `git diff` と `git status` を採取して比較(未追跡ファイルは diff に出ない)。差分があれば判定を無効にする | 検出であって防止ではない。無効にした後に作業ツリーを戻す手順が要る |

3 層目はモデルや版が変わっても効く唯一の層なので省かない(第 5 章の `phase-loop` に組み込んである)。

### 実装役と審査役を同じモデル・似た指示にしない

同じモデルは同じ見落としをする。審査役の本文は実装役の写しから作らず、「疑う」「測り直す」「信じない」を軸に別に書く。
陽性コントロールは**方法を書く**(「隔離コピーで実装を壊してテストが落ちることを示す」)。方法を書かないと、安いモデルは「不正入力に invalid が返る」のような弱い確認で済ませる △(4 回中 3 回)。

### description は委譲の判断材料

`description` はスキルと違って人が選ぶときは効かないが、本体が**自動で委譲するか**の判断に使われる ◎。
「審査役。コードは直さない」のように、やること・やらないことを書く。委譲させたくないなら `disable-model-invocation: true`。

## 3.5 委譲のコストと使い分け

同じフェーズゲート 1 周を、人が 2 セッションに分けて回した場合と、本体 1 セッションからサブエージェントに委譲した場合の実測(2026-10-19、各 1 回 △。AI credits は使用量の課金単位で、入出力トークンから換算される):

| 方式 | 消費(AI credits) | 主因 |
| --- | ---: | --- |
| 手動 2 セッション(実装役・審査役を別々に起動) | 0.96 | 役ごとの消費がそのまま |
| 本体 1 セッションから委譲 | 2.01 | 本体が文脈を持ち続ける代金(本体だけで 0.82)。委譲されたサブエージェント単体は手動より安い |

含意: 委譲は便利だが、**本体の文脈を溜めない**ことが安さの条件。基準値取りや小さなフェーズは手動 2 セッション、量産は委譲でもよいが本体は「渡すだけ」にする。
委譲が本当に起きたかは、セッションの使用量表示で確かめる(本体とサブエージェントの消費が分かれて出る △)。「委譲したつもり」が静かに起きていないことがある。

## 3.6 目で確認する

| 確認 | 方法 |
| --- | --- |
| 登録されたか | `/agent` の一覧に出る。出なければ場所か拡張子(`.agent.md`)が違う |
| ツール制限が効いているか | 審査役を選び「`src/` の 1 行を直して」と頼む。断って FAIL 相当の報告を返すこと |
| 委譲が起きたか | 本体に「審査役に審査させて」と頼み、使用量表示にサブエージェントの消費が分かれて出ること |
| 指示が届いているか | 委譲で呼んだ審査役に「このリポジトリの前提を復唱して」と頼む(`include-custom-instructions` の確認) |
| アプリで見えるか | アプリでリポジトリを開き `/agent` に出ること |

## 3.7 落とし穴

- **ツール名の綴りを間違えた。** 知らない名前は黙って無視され ◎、`tools: ["raed"]` は「全部禁止」ではなく「無視」になる。審査役が思ったより多くのツールを持っている可能性があるので、第 3.6 節の確認を省かない。
  許可リストの書き方でツールが**静かに消える**(状態は正常のまま)事例もある △。
- **個人用の同名定義が勝つ。** `~/.copilot/agents/reviewer.agent.md` があると、リポジトリの `reviewer` は使われない ◎。スキルとは逆(スキルはリポジトリが優先)なので混同しやすい。
- **`infer` と `disable-model-invocation` のどちらを書くか。** 共通リファレンスは `infer` を廃止扱い ◎、CLI のリファレンスは `infer` だけを載せる ◎。委譲を止めたいときは両方書いて手元の環境で確かめる △。
- **本文に手順を書いた。** HARNESS.md と食い違う。本文は規則と報告形式だけ。
- **委譲に全部任せて本体が重くなった。** 第 3.5 節。本体は渡すだけにする。
