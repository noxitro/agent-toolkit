# 2. スキル — 特定の作業の手順書

## これは何

「この作業はこうやる」をまとめた手順書です。
エージェントは普段、スキルの**名前と説明文(description)だけ**を見ていて、依頼が説明文に合ったときに中身を読みます。
だから、いくつか置いても毎回の会話が重くなりにくいのが特徴です。

スキルの形式は共通の規格なので、Copilot 以外のエージェントでもそのまま使えます。

## 置き場

```text
.github/skills/
└── build-and-test/      ← フォルダ名 = スキルの名前
    └── SKILL.md
```

## 例

```markdown
---
name: build-and-test
description: ビルドやテストを頼まれたとき、またはビルドが失敗した原因を調べるときに使う(例:「ビルドして」「テストを回して」)。新しいテストを書く作業には使わない。
---

# ビルドとテスト

1. `cmake --build build` を実行する。失敗したら、出力の最後の 20 行を見せて止まる。
2. `ctest --test-dir build --output-on-failure` を実行し、成功と失敗の数を報告する。
3. テストのコードは変えない。
```

上の `---` で囲んだ部分に、名前(`name`)と説明文(`description`)を書きます。その下が手順です。

## いちばん大事なのは説明文

説明文は「中身の要約」ではなく、**どんな依頼のときに使うか**を書きます。

| よくない | よい |
| --- | --- |
| ビルドとテストの手順 | ビルドやテストを頼まれたときに使う(例:「ビルドして」)。新しいテストを書く作業には使わない。 |

- 普段の頼み方(「ビルドして」など)をそのまま入れる。
- **使わない場面**も 1 つ書く。似たスキルと取り合いにならないように。
- スキルが呼ばれないとき、直すのは本文ではなく説明文。

## 作り方: エージェントに頼む

```text
「〇〇」の作業をスキルにしたい。.github/skills/〇〇/SKILL.md を作って。
description には、どんな依頼のときに使うかと、使わない場面を書いて。本文は手順を短く。
```

## 効いているか確かめる

- 使ってほしい頼み方で依頼する → スキルを読み込んだ表示が出れば OK。
- `/スキル名` と打つと、名前を指定して直接呼べる。
- 一覧で見るなら、アプリは Customize → Skills、CLI は `/skills list`。

## コツは 3 つ

- **1 つのスキルに 1 つの作業。**
- **増やしすぎない。** 使っていないものは消す。
- **毎回守ってほしいことなら、スキルではなく[指示](01-instructions.md)へ。**

## 育て方

呼ばれてほしいのに呼ばれなかったら、そのときの頼み方を説明文に足します。
呼ばれなくていいのに呼ばれたら、「〜には使わない」を説明文に足します。
