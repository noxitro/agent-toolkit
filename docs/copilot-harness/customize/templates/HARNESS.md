# 開発ハーネス — {{プロジェクト名}}(フェーズゲート方式)

> **使い方**: リポジトリのルートに `HARNESS.md` としてコピーし、`{{ }}` を埋める。
> エージェント定義 `.github/agents/implementer.agent.md` / `reviewer.agent.md` と
> 起動スキル `.github/skills/phase-loop/SKILL.md` をあわせて置く。
> 設計・要件は `{{docs/PLAN.md}}` に置き、ここには「誰が・どの順で・何を満たしたら次へ進むか」だけを書く。

このリポジトリは「実装 → レビュー(E2E) → ゲート通過」のループでフェーズを進める。
PASS しない限り次フェーズへ進まない。

## 役割

| 役割 | 担い手 | 責務 |
| --- | --- | --- |
| オーケストレータ | 人間(リーダー)または `phase-loop` を実行するチャット | フェーズ分割・派遣・審査前後の差分採取・ゲート通過時の差分確認・記録。コミットは人の指示で行う。実装はしない |
| 実装 | `implementer` エージェント | スコープ内の実装・ビルド・テスト・自己検証・定型報告。コミットしない。テストコードを変えない |
| レビュー / QA | `reviewer` エージェント | 静的レビュー + 実行環境での E2E(実際に動かす検証)+ 陽性コントロール → VERDICT。コード修正禁止。テスト差分とログの生出力を自分で確認する |
| 人(担当者・リーダー) | 作業者 | 周回上限・テスト変更・設計判断で呼ばれたら判断する。審査結果を手で書き換えない |

## フロー(各フェーズ共通)

```text
オーケストレータ: フェーズのスコープを implementer に委譲
  → implementer: 実装 + ビルド/テスト成功 + 自己検証 → 定型報告(困ったら止めて報告してよい)
  → オーケストレータ: 審査前の差分を採取(git diff と git status → e2e-artifacts/phase-N-before-review.*)
  → オーケストレータ: reviewer に「フェーズ番号 + ゲート条件」でレビュー依頼
  → reviewer: テスト差分の確認 + 自分で測り直し + 陽性コントロール + 意地悪テスト → VERDICT
  → オーケストレータ: 審査後の差分を採取し、審査前と比較。差分があれば判定を無効にして再審査
  → FAIL: 指摘(再現手順付き)を implementer に渡して修正 → 再レビューは同じ再現手順の再実行で閉じる
          (最大 3 周。超えたら止まり、人に戻す。人がフェーズを分割するか要件を見直す)
  → PASS: オーケストレータが差分を確認 → 人が commit(phase-loop のチャットは指示があるまでコミットしない)
          → TEST_REPORT.md 更新 → phase-log.csv に 1 行追記 → 次フェーズへ
```

## 運用ルール

- **PASS しない限り次フェーズへ進まない。** 「後で直す」は TEST_REPORT.md の未検証欄に理由付きで残す。
- **レビュー役はコードを直さない。** 直したくなったら FAIL。
- **レビュー役は自分で測り直す。** 実装役の報告も TEST_REPORT.md の文章も入力であって証拠ではない。
  テストディレクトリ(`{{tests/}}`)の差分と、テスト実行ログの生出力を自分で開く。
- **テストコードの変更は既定で FAIL。** テストの削除・スキップ・期待値の変更・アサーションの緩和・
  タイムアウトの延長・対象外ディレクトリへの移動は、TEST_REPORT.md「テスト変更の承認記録」に
  人の承認(日付・承認者・理由)が無い限り通さない。実装役はテストを変えたくなったら止めて報告する。
- **外部 API は版の文書を根拠にする。** 実装役は、使った外部 API(SDK・ライブラリ・OS/ランタイムの API)
  ごとに、**インストール済みの版**の文書かヘッダの該当箇所(ファイルパスと行、または URL と版)を報告に添える。
  シグネチャだけでなく、**既定値・戻り値・エラー時の挙動**が版の間で変わっていないかを確認する。
  根拠の無い API 利用は審査役が FAIL にする。
- **審査の前後で差分を採取する。** オーケストレータは審査依頼の直前と直後に `git diff` と `git status --porcelain` を採取して比較する
  (未追跡ファイルの追加は diff に出ない)。
  審査役の実行後に作業ツリーが変わっていれば、その判定は無効(審査役が編集したか、別の何かが動いた)。
- **陽性コントロールと陰性コントロール**: 各フェーズのレビューで、少なくとも 1 つのゲート条件について
  「壊せば検出される」ことを示す(陽性)。ハーネス導入時と審査役のモデルや指示を変えたときは、
  正しい実装で PASS が出ること(陰性)も確認する(付録 B)。
- **未検証は理由付きで残す。** 環境起因(実行環境が無い・外部アカウント待ち)は時間を区切って見切り、➖ として記録して先へ進む。
- **周回上限に達したら止めて人に戻す。** 3 周で PASS しなければ、オーケストレータは実装も審査も続けず、
  周回ごとの指摘の推移を担当者に報告して止まる。担当者はリーダーに連絡し、フェーズ分割か要件見直しを決める。
  上限を超えて回し続けることも、上限を増やすことも、現場では行わない(HARNESS.md を直してからにする)。
- **実装役は困ったら止めて報告してよい。** 解釈が割れる、ゲート条件が確認できない、テストを変えないと
  通らない、根拠となる文書が見つからない。いずれも「止めて報告」が正しい動きで、減点ではない。
- **証拠の置き場**: `{{e2e-artifacts/}}`(gitignore 対象)。レポートからはファイル名で参照。
- **完了報告は定型**(implementer / reviewer の `.agent.md` に書いた形式)。「未解決事項」欄が次のレビュー観点の供給源。
- **フェーズ終了時に 1 行記録する。** `docs/phase-log.csv` に「日付, フェーズ, タスク, 実装役モデル, 審査役モデル,
  周回数, 判定, 人の介入時間(分), 備考」を追記する(手順は phase-loop 側)。
- **チャットが途中で落ちたら**: 作業ツリーは残っているので、同じフェーズ番号で `phase-loop` を再開する。

## フェーズとゲート条件

ゲート条件は「レビュー役が機械的に確認できる形」で書く。「正しく動く」は条件ではない。
「{{コマンド}} の終了コードが 0」「{{画面}} で {{要素}} が表示される(スクリーンショット)」
「{{値}} が仕様書の値と一致する」のように書く。

### Phase 0: 環境構築

- [ ] ビルドコマンドが成功する
- [ ] テストコマンドが成功する(0 件でもよいが実行できること)
- [ ] {{起動確認の方法。例: `./app --version` が終了コード 0 で終わる}}

Phase 0 の PASS がそのまま陰性コントロールになる。PASS の後に人が付録 B の陽性コントロールを行い、
両方の結果を TEST_REPORT.md の Phase 0 に書く。

## オーケストレータの最終確認(各ゲート通過時・軽量)

- 実装役の報告と審査役の PASS 報告を突き合わせ、スコープ逸脱・設計乖離が無いか差分を確認
- 審査前後の差分が一致していることを確認(一致しなければ判定無効)
- テストディレクトリに差分があれば、承認記録があることを確認
- 問題なければ人がコミットし、オーケストレータが TEST_REPORT.md の該当セルの更新案と phase-log.csv の 1 行を提示してフェーズ完了を宣言
- 深掘りが必要なときだけコードを読む

## 付録 A: 順調と判断してよい条件 / 疑うべき兆候

ハーネスが「回っている」ことと「検証している」ことは別。週に 1 回、リーダーが次を見る。

### 順調と判断してよい条件

- [ ] FAIL が出たフェーズがある(全フェーズが 1 周目 PASS ではない)
- [ ] FAIL の指摘に再現手順が付いていて、担当者がその手順を自分で再実行できた
- [ ] 審査役の報告に、実行したコマンドの生出力(末尾の行、件数、終了コード)が貼られている
- [ ] 審査前後の差分が毎フェーズ一致している
- [ ] 陽性コントロールで壊した内容がフェーズごとに違う
- [ ] phase-log.csv の周回数が 1〜3 の間でばらついている
- [ ] 実装役が「止めて報告」した例が 1 件以上ある

### 疑うべき兆候

- [ ] 全フェーズが 1 周目で PASS している
- [ ] 判定文が毎回ほぼ同じ長さ・同じ文面(テンプレートの穴埋めだけで測っていない)
- [ ] 審査役の報告にテストの再実行が無い(実装役の件数をそのまま書いている)
- [ ] 陽性コントロールが毎回同じ(「ビルドを壊す」だけ、など)
- [ ] 実装役と審査役が同じモデルで、指示文も似ている(同じ見落としを共有する)
- [ ] テストディレクトリの差分が増えているのに承認記録が増えていない
- [ ] 外部 API の根拠欄が「公式ドキュメント」「一般的な使い方」など版と場所を特定しない書き方
- [ ] 審査役の報告が TEST_REPORT.md の文章を引用して根拠にしている
- [ ] 周回上限に達したフェーズが 0 件のまま、スコープの大きいフェーズが PASS している
- [ ] 人の介入時間が毎フェーズ 0 分

兆候が 2 つ以上当たったら、付録 B の陽性コントロールをそのフェーズでやり直す。

## 付録 B: 陽性コントロールと陰性コントロールの手順

**陽性コントロール**は「審査役が壊れた実装に FAIL を出せるか」、**陰性コントロール**は「正しい実装に PASS を出せるか」。
どちらか一方では検査にならない(全部 FAIL にする審査役も、全部 PASS にする審査役も、検出していない)。

### 手順(ハーネス導入時、審査役のモデルや指示を変えたとき、付録 A の兆候が出たとき)

1. 正しい実装の状態で `reviewer` にそのフェーズを審査させ、PASS が出ることを確認する(陰性)。
   FAIL が出たらゲート条件か審査役の指示が厳しすぎる。直してから次へ。
2. 作業ツリーのコピー(ブランチか別ディレクトリ)で、下のサンプルのどれか 1 つをわざと入れる。
   テストが通る壊し方を選ぶ(テストで落ちる壊し方は審査役ではなくテストの検査になる)。
3. 同じゲート条件で `reviewer` に審査させ、FAIL が出て、指摘がその壊した箇所を指していることを確認する(陽性)。
4. 結果(日付・壊した内容・判定・指摘が箇所を指したか)を TEST_REPORT.md の該当フェーズに書く。
5. 壊した変更を破棄し、正しい状態に戻ったことを `git status` で確認する。

### サンプル(壊し方の型)

| 型 | 壊し方 | 審査役が見るべき根拠 |
| --- | --- | --- |
| **既定値の意味が変わった API** | 依存ライブラリを更新した後も、外部 API の引数を省略して更新前の既定値を前提にした呼び出しを入れる。例: 更新前は `timeout=0` が「無期限」、更新後は「即時失敗」。または更新前は「エラーは例外」だった関数が更新後は「戻り値 -1」になっているのに戻り値を見ない | インストール済みの版の文書・ヘッダで該当引数の既定値と戻り値を確認し、「版 X.Y.Z の文書 path:line」を根拠に FAIL。文書を見ずに「正しそう」で通したら検出失敗 |
| 期待値の書き換え | テストの期待値を実装の出力に合わせて変える(テストは通る) | テストディレクトリの差分 + 承認記録の有無。無ければ FAIL |
| 無効化 | テストを skip 属性で止める、対象外ディレクトリへ移す | 同上。テストの実行件数が前フェーズより減っていないかも見る |
| 境界の取り違え | 配列長 N の比較を `<=` にする、0 と 1 の起点を混ぜる | 意地悪テスト(境界値)で検出。文言どおりの正常系だけでは通る |
| 仕様書との不一致 | 対応表の値を 1 つだけ仕様書と違う値にする | 自分で仕様書を開いて値を突き合わせる。TEST_REPORT.md の表の値を信じたら検出失敗 |

「既定値の意味が変わった API」型は、シグネチャが同じまま挙動が変わるので、コードを読むだけでは見つからない。
審査役に版の文書を開かせる唯一の方法が、この型の陽性コントロールを定期的に入れることである。
